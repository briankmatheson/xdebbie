xdebbie `7152883` / 0.15.0-2, both installed on gram and timesink).
Delivered as abe 0.5.0 (`abe-block-exporter`, HEAD `9266c27`) and xdebbie

## Why not the kernel's NVMe/TCP TLS

Linux nvmet/nvme-tcp do TLS 1.3, but only with **pre-shared keys**
(`--tls`, `--psk`, `tlshd` on both sides, keys in the kernel keyring): there
is no x.509 at either end, so it would not have let the cluster CA decide
who may read a volume. It would have added a PSK distribution problem
(xdebbied would have to mint, store and rotate a key per host pair, and
`tlshd` would become a boot dependency on every hypervisor) to buy
encryption that the WireGuard underlay already provides between gram and
timesink. DH-HMAC-CHAP (in-band auth) has the same key-distribution shape
and is still PSK-like. The fence gives the property we actually wanted — a
port is readable only from the box that asked for it — using what already
authenticates the ask: the client certificate on the API call, and the fact
that `nvme connect` in xdebbie is always local to the caller
(`attach_volume` refuses remote hosts; the ABE call and the connect leave
from the same underlay address). `allowed_hosts` by hostnqn was skipped
for the same reason: unverifiable without in-band auth.

## Adoption on upgrade

Every export made by 0.4.0 has an `abe_port` tag and no `abe_client`. When
0.5.0 starts, `fence_rebuild` runs before any port is re-exported, so the
window where a port is open to everyone is zero. For each tag-less export
it looks for established connections to that port: exactly one peer is
adopted (fence opened to it, tag written); none or several leave the port
closed and the id in `reexport.closed`. On timesink, node0's live disk is
connected from `10.22.0.1` itself, so the upgrade adopts it and the VM
never notices. On gram, where nothing was attached, those volumes come
back closed, and xdebbied's next reconcile (endpoint refresh → `GET /id`)
opens each to gram — the same path that already handled "ABE moved my
port" in 0.15.0, which is why xdebbie needed no new call sites for the
fence.

## Conflicts with the spec as written

- Spec §3.2 says `xdctl host show <name>` prints the abe URL with `tls`;
  `show` is an alias of `host ls` (there is no per-host text view, only
  `describe`, which is JSON). The marker went into `host ls` as a `TLS`
  column and into `describe` as `abeCapacity.tls`; the URL is in
  `describe` as before.
- Spec §3.1 says a TLS failure "surfaces as `AbeHttpError`". It does, with
  `status: 0`; `http_status()` deliberately reads that as `None` so no
  caller mistakes it for an HTTP reply.
- Spec §3.3 suggested `bootstrap::api_tls::generate_localhost` for the
  run.sh certs; it is a `pub(crate)` test hook with no CLI, so run.sh uses
  `openssl` (eight lines) rather than growing a hidden subcommand.
