# xdebbied Bootstrap

This document describes the self-bootstrapping functionality added to `xdebbied`, enabling single-binary deployment to stock Debian 13 systems.

## Overview

The bootstrap functionality automatically:

1. **Checks and installs dependencies** (libvirt, QEMU, cloud-localds)
2. **Ensures libvirtd is running** and enabled
3. **Discovers existing libvirt resources** (networks, storage pools)
4. **Creates default resources** if none exist:
   - Network: `xdebbie` on `10.23.0.0/16` with bridge `virbr-xdebbie` at `10.23.<box>.1`
   - Storage pool: `xdebbie` at `/var/lib/libvirt/xdebbie`
5. **Generates configuration** at `/etc/xdebbie/xdebbied.toml`
6. **Generates secure API token** at `/etc/xdebbie/token`
7. **Creates environment file** at `/etc/xdebbie/xdebbie_env` for `xdctl`

## Usage

### Option 1: Explicit Bootstrap Command

Run the bootstrap command first, then start the server:

```bash
# As root (for dependency installation and libvirt access)
sudo xdebbied bootstrap

# Start the server
sudo xdebbied serve
```

### Option 2: Bootstrap on First Run

Start the server with the `--bootstrap` flag:

```bash
sudo xdebbied serve --bootstrap
```

This will run bootstrap automatically before starting the server. If bootstrap fails, it will log a warning and continue (useful if already configured).

### Option 3: Default Serve (Existing Behavior)

If already bootstrapped, just run:

```bash
sudo xdebbied serve
```

This assumes configuration and resources are already set up.

## Command-Line Options

### `xdebbied bootstrap`

Bootstrap the system with automatic resource discovery and creation.

**Options:**

- `--force` - Regenerate the configuration and token. The old files are kept as `.bak-<timestamp>`; operator settings (`volume_group`, `thin_pool`, `tls_*`, `advertise_url`, `policy`, `[network]`, `[mesh]`, `[[hosts]]`) are carried into the new config. A config that exists but does not parse is never replaced without `--force`
- `--uri <URI>` - Libvirt URI (default: `qemu:///system`)
- `--network <NAME>` - Network name to create (default: `xdebbie`)
- `--subnet <CIDR>` - Overlay subnet (default: `10.23.0.0/16`). One /16 for the cluster; box N's bridge is `<subnet>.N.1`, its VMs `<subnet>.N.2-254`
- `--pool <NAME>` - Storage pool name (default: `xdebbie`)
- `--pool-path <PATH>` - Storage pool path (default: `/var/lib/libvirt/xdebbie`)
- `--box <0-253>` - Mesh box id to ask for. Normally not needed: the first box takes `0` and every box that joins is **assigned the next free id by the CA box** at approval (a host that re-enrols keeps the id it had). The id goes into `[mesh]`, and the libvirt network bootstrap creates gets the bridge MAC `52:54:00:23:<box>:fe` the mesh's derived FDB scheme expects — which is why enrolment happens before the network is created. For a network that already exists bootstrap only warns when the MAC differs. With `--join`, `--box` is a wish the CA box honours only if that id is free

**Examples:**

```bash
# Standard bootstrap
sudo xdebbied bootstrap

# Custom network
sudo xdebbied bootstrap --network internal --subnet 10.100.0.0/16

# Force re-bootstrap
sudo xdebbied bootstrap --force
```

### `xdebbied serve`

Start the API server and reconciler.

**Options:**

- `--bootstrap` - Run bootstrap before starting server
- `-c, --config <PATH>` - Configuration file path (default: `/etc/xdebbie/xdebbied.toml`)

**Examples:**

```bash
# Start with bootstrap
sudo xdebbied serve --bootstrap

# Start with custom config
sudo xdebbied serve --config /tmp/my-config.toml
```

### `xdebbied check`

Check connectivity to all configured hosts.

## Files Created

### Configuration: `/etc/xdebbie/xdebbied.toml`

```toml
# xdebbied configuration
# Auto-generated by xdebbied bootstrap

listen = "0.0.0.0:7443"
state_file = "/var/lib/xdebbie/state.json"
token_file = "/etc/xdebbie/token"

policy = "spread"
reconcile_interval_secs = 5
host_stale_secs = 60

virsh = "virsh"
seed_command = ["cloud-localds", "--network-config={net}", "--vendor-data={vendor}", "{out}", "{user}", "{meta}"]

[[hosts]]
name = "hostname"
uri = "qemu:///system"
failure_domain = "default"
bridge = "virbr-xdebbie"
storage_pool = "xdebbie"
cpu_overcommit = 2.0
mem_overcommit = 1.0
reserved_cpus = 2
reserved_memory_mib = 4096
control_plane_eligible = true
```

### Token: `/etc/xdebbie/token`

64-character hexadecimal token (32 random bytes), root:root mode 0400:

```
a1b2c3d4e5f6...
```

### Environment: `/etc/xdebbie/xdebbie_env`

Root:xdebbie mode 0440. Bootstrap creates the `xdebbie` system group;
add an operator account to it (`sudo usermod -aG xdebbie $USER`, then
log in again) and that account can `source` the file and run `xdctl`
without sudo. Nobody else can read it.

```bash
# xdebbie environment variables
# Source this file: source /etc/xdebbie/xdebbie_env

export XDEBBIE_URL=https://gram.example.net:7443
export XDEBBIE_TOKEN='a1b2c3d4e5f6...'
export XDEBBIE_CA=/etc/xdebbie/api-ca.pem
```

`XDEBBIE_URL` is the config's `advertise_url` (the hostname, never
`0.0.0.0`), so the same file works from another machine.

### API TLS and the cluster CA: `/etc/xdebbie/api-*.pem`

There is **one CA per cluster**. The first box bootstrapped generates it
(in-process with `rcgen`; no openssl needed) and keeps the key; it signs
every other box's certificate through *enrolment* (next section). Bootstrap
writes `tls_cert`/`tls_key` into the config, so the API serves **HTTPS from
the first start**; the bearer token and the WireGuard public keys exchanged
during mesh enrolment never cross the LAN in clear.

| File | Owner | Mode | Purpose |
|---|---|---|---|
| `api-ca.pem` | root:xdebbie | 0440 | cluster CA cert; what `xdctl` trusts (`XDEBBIE_CA`) |
| `api-ca-key.pem` | root:root | 0400 | CA key — **first box only**; signs `xdctl approve` |
| `api-cert.pem` | root:xdebbie | 0440 | this box's cert (SANs: hostname, FQDN, every local IPv4; serverAuth + clientAuth) |
| `api-key.pem` | root:root | 0400 | this box's key |
| `peers/*.pem` | root:xdebbie | 0440 | extra CAs to trust (rarely needed now) |

On the CA box, `--force` reissues the server cert but **keeps the CA**
(members' certs chain to it). A box upgraded from 0.13 has certs but no CA
key: run `bootstrap --force` there once if it is to be the CA box, or
`bootstrap --join` if another box is. The server cert lists the host's
IPv4 addresses at generation time; if the address changes,
`xdebbied bootstrap --force` reissues it.

Every daemon presents its own cert when it talks to another box (leader
forwarding, token distribution, enrolment forwarding), and every daemon
accepts a client cert signed by the cluster CA in place of a bearer
token. That is how a new box gets the token in the first place.

### Joining a cluster: enrolment and approval

Nothing to copy by hand. A plain `sudo xdebbied bootstrap` on a
new box first **listens 20 s on the discovery group** (239.0.0.42:7442)
for a running cluster. If it hears one it shows what it found (leader
first) and asks `Join it via https://gram…:7443? [Y/n/other URL]`; if it
hears nothing it asks for a URL, and Enter means "this is the first box"
(a new cluster; this box keeps the CA key). Without a terminal — the
package's first-install bootstrap — a found cluster is an error telling
you to re-run with `--join`, never a silent second cluster; silence means
first box. Skip the listening with `--join <url>` or `--standalone`
(`--discover-secs N` tunes it, 0 disables). A box that already holds the
CA key, or has `ca_url` in its config, never asks.

Explicitly, with the CA fingerprint that bootstrap printed on the CA box
(or `xdctl ca`):

```bash
sudo xdebbied bootstrap --join https://gram.example.net:7443 \
     --ca-fingerprint sha256:3fa1…        # optional; without it you are asked y/N
```

The joiner fetches the CA, pins it, generates a key (`api-key.pem`, never
leaves the box) and a CSR, posts it to `POST /v1/enroll` and waits,
printing the key fingerprint. From any member (CA box or not — requests
are forwarded to the CA box via `ca_url`):

```bash
xdctl enroll ls                 # ID  HOST  BOX  URL  FINGERPRINT  STATUS  AGE
xdctl approve timesink          # == xdctl enroll approve; by hostname or id
xdctl enroll deny <id>          # the box can ask again with --join --force
xdctl enroll ls --all           # include approved / denied
xdctl ca                        # CA PEM + fingerprint, to check against --join
```

On approval the CA box signs the CSR and **assigns the box id** (lowest
free `0-253`, counting its own `[mesh]` box and peers plus every pending or
approved enrolment; `enroll ls` shows it in the BOX column). The joiner
picks up the certificate within seconds, installs `api-cert.pem` +
`api-ca.pem`, writes the id to `[mesh] box` and creates its bridge with the
matching MAC, then fetches the
**cluster token** over mTLS (`GET /v1/enroll/token`, client-certificate
only) and writes `/etc/xdebbie/token` and `xdebbie_env`. Bootstrap then
finishes as usual. The joiner's config gets `ca_url = "https://gram…"`
so later `xdctl approve` calls made against it are forwarded.

The joiner also copies the **overlay network** from the CA box
(`GET /v1/network` over mTLS): same `cidr` and `domain`, and this box's own
/24 of it — bridge `<cidr>.<box>.1` as gateway and DNS, VMs
`.<box>.2`–`.254` as the pool — so pools are disjoint by construction
(docs/network.md). A kept config gains the block only if it has no live
`[network]`; a regenerated one gets it in place of the template. If the CA
box still allocates from the whole subnet, bootstrap warns with the
`pool_end` to set there. No `[network]` on the CA box means the joiner's is
generated locally, as for a first box.

Re-running `bootstrap --join` resumes a pending enrolment (state in
`/var/lib/xdebbie/join.json`); `--force` starts over with a new key.
Pending requests live in `/var/lib/xdebbie/enroll.json` on the CA box
(at most 64; the rest are refused). `--join` refuses plain `http://`.

`xdctl --insecure` (or `XDEBBIE_INSECURE=1`) skips verification for a lab.

### State: `/var/lib/xdebbie/state.json`

Created at runtime to persist VM and host state.

## Libvirt Resources

### Network: `xdebbie`

- **Bridge**: `virbr-xdebbie`, MAC `52:54:00:23:<box>:fe`
- **Subnet**: `10.23.0.0/16`; this bridge at `10.23.<box>.1`
- **DHCP**: none from libvirt — xdebbied's own responder serves `10.23.<box>.2-254` (docs/network.md)
- **Autostart**: Enabled

Created with (box 1 shown):

```xml
<network>
  <name>xdebbie</name>
  <bridge name='virbr-xdebbie' stp='off' delay='0'/>
  <mac address='52:54:00:23:01:fe'/>
  <dns enable='no'/>
  <ip address='10.23.1.1' netmask='255.255.0.0'>
  </ip>
</network>
```

### Storage Pool: `xdebbie`

- **Type**: Directory
- **Path**: `/var/lib/libvirt/xdebbie`
- **Permissions**: 0711, owner:group 0:0
- **Autostart**: Enabled

Created with:

```xml
<pool type='dir'>
  <name>xdebbie</name>
  <target>
    <path>/var/lib/libvirt/xdebbie</path>
    <permissions>
      <mode>0711</mode>
      <owner>0</owner>
      <group>0</group>
    </permissions>
  </target>
</pool>
```

## Dependencies

The bootstrap process checks for and installs (if running as root):

- **libvirt-daemon-system** - Libvirt daemon and system utilities
- **libvirt-clients** - `virsh` command-line tool
- **qemu-kvm** - KVM virtualization
- **qemu-utils** - `qemu-img` and other utilities
- **cloud-image-utils** - `cloud-localds` for NoCloud seed generation

On Debian/Ubuntu, these are installed via:

```bash
sudo apt-get update
sudo apt-get install -y libvirt-daemon-system libvirt-clients qemu-kvm qemu-utils cloud-image-utils
```

## Bootstrap Process Flow

```
1. Check Dependencies
   ├─ virsh, qemu-system-x86_64, qemu-img, cloud-localds
   └─ Missing and root → apt-get install; not root → error with package list

2. Ensure libvirtd Running
   └─ systemctl is-active / start / enable libvirtd

3. Discover Resources
   └─ virsh net-list, pool-list → bridges and pool paths

4. Identity
   ├─ --join: discovery listen (20 s) unless --join/--standalone given;
   │   pin the cluster CA, POST /v1/enroll, wait for `xdctl approve`,
   │   install api-cert.pem + api-ca.pem, fetch the cluster token;
   │   the CA assigns the box id; then GET /v1/network to copy the overlay
   └─ first box: generate token, cluster CA and this box's cert; box 0

5. Create Resources (if needed)
   ├─ No xdebbie network → net-define (no DHCP range, MAC from box id)
   ├─ Existing one: warn if its MAC is not the box's; read its XML — no
   │   <dhcp> means [network] is written live with its subnet
   └─ No xdebbie pool → mkdir + pool-define + pool-start + pool-autostart

6. Generate Configuration
   ├─ Exists and not --force → keep; set [mesh] box, ca_url, and add a
   │   [network] copied from the cluster if there is none
   ├─ Exists and --force → back up, regenerate, carry operator settings over
   └─ Network and pool chosen by the names ensured in step 5

7. libvirt TLS (cluster CA)
   ├─ /etc/pki/CA/cacert.pem, /etc/libvirt/pki/{cacert,servercert}.pem,
   │   /etc/pki/libvirt/clientcert.pem ← api-ca.pem / api-cert.pem (+ keys)
   ├─ libvirtd.conf: listen_tls on the overlay bridge address, client
   │   certs verified against the cluster CA
   ├─ libvirtd-tls.socket enabled; libvirtd restarted when anything moved
   └─ Warn if the cert has no SAN for the listen address (re-enrol --force)

8. Firewall (ufw) from the config

9. Register with the cluster (--join only)
   └─ PUT /v1/hosts/<fqdn> at the CA box (forwarded to the leader):
       the local [[hosts]] entry with uri = qemu+tls://<listen address>/system
```

Every box's libvirt trusts every other box's client certificate because
they are all issued by the one cluster CA; nothing is copied by hand. The
leader reaches a box's libvirtd on its overlay bridge address, i.e. across
the Geneve mesh, so a freshly joined box shows in `xdctl host ls` at once
but turns `Ready` once `xdctl mesh peer add` has been done both ways
(docs/mesh.md).

## Resource Discovery

If libvirt networks or storage pools already exist, bootstrap will:

1. **Discover them** via `virsh net-list` and `virsh pool-list`
2. **Use the first available** network and pool in the generated configuration
3. **Skip creating defaults** if resources already exist

This allows bootstrap to work on systems with existing libvirt setups (e.g., `default` network and pool).

## Security Considerations

### Token Security

- Token is 32 random bytes (256 bits of entropy)
- Token file and `token.previous` (during a rotation) are root:root 0400;
  `xdebbie_env` and `xdebbied.toml` are root:xdebbie 0440. All are written
  to a temp file with the final mode and renamed into place, so a secret
  is never world-readable even for an instant
- The API serves HTTPS by default with a bootstrap-generated certificate,
  so the token never travels in clear
- Never logged or displayed except in environment file
- Bearer token authentication for all API requests

### Root Privileges

Bootstrap requires root for:

- Installing packages via `apt-get`
- Starting/enabling `libvirtd` service
- Creating libvirt networks (bridges require privileges)
- Writing to `/etc/xdebbie/` and `/var/lib/xdebbie/`

The server itself can run as root or as a user with libvirt group membership.

### Network Isolation

The default `xdebbie` network is NAT-isolated:

- VMs can reach external networks
- External networks cannot initiate connections to VMs
- VMs can communicate with each other on the bridge

## Integration with Cluster API

Once bootstrapped, xdebbied can serve as the infrastructure provider for CAPQ (Cluster API Provider Qfodufk8s):

1. **Bootstrap** the host system:
   ```bash
   sudo xdebbied bootstrap
   ```

2. **Start xdebbied**:
   ```bash
   sudo xdebbied serve
   ```

3. **Configure environment** for xdctl (root shell; the file is 0400):
   ```bash
   sudo -s
   source /etc/xdebbie/xdebbie_env
   ```

4. **Verify connectivity**:
   ```bash
   xdctl host ls
   ```

5. **Deploy CAPQ** to your management cluster and create `QfodufkCluster` resources

## Troubleshooting

### Bootstrap fails with "not running as root"

If not root, bootstrap cannot install dependencies or start services. Either:

- Run `sudo xdebbied bootstrap`
- Manually install dependencies first, then run as non-root user in libvirt group

### Bootstrap fails with "Failed to connect to libvirt"

Ensure libvirtd is running:

```bash
sudo systemctl status libvirtd
sudo systemctl start libvirtd
```

### Network creation fails with "bridge already exists"

An existing bridge may conflict. Options:

- Use existing network: `xdebbied bootstrap --network default`
- Choose different name: `xdebbied bootstrap --network mynet`
- Remove conflicting bridge: `sudo ip link delete virbr-xdebbie`

### "Permission denied" when starting xdebbied

Token file or state directory permissions may be wrong. Check:

```bash
ls -la /etc/xdebbie/
ls -la /var/lib/xdebbie/
```

`token`, `token.previous` and `api-key.pem` should be root:root 0400;
`xdebbied.toml`, `xdebbie_env`, `api-ca.pem` and `api-cert.pem`
root:xdebbie 0440; the directory and `peers/` root:xdebbie 0750.
Re-running `xdebbied bootstrap` (without `--force`) repairs ownership
without touching content.

## Comparison with Manual Setup

**Before (Manual)**:

```bash
# 1. Install dependencies
sudo apt-get update
sudo apt-get install -y libvirt-daemon-system libvirt-clients qemu-kvm qemu-utils cloud-image-utils

# 2. Start libvirtd
sudo systemctl start libvirtd
sudo systemctl enable libvirtd

# 3. Create network
cat > /tmp/network.xml <<EOF
<network>
  <name>xdebbie</name>
  <bridge name='virbr-xdebbie'/>
  <ip address='192.168.100.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='192.168.100.100' end='192.168.100.250'/>
    </dhcp>
  </ip>
</network>
EOF
sudo virsh net-define /tmp/network.xml
sudo virsh net-start xdebbie
sudo virsh net-autostart xdebbie

# 4. Create storage pool
sudo mkdir -p /var/lib/libvirt/xdebbie
cat > /tmp/pool.xml <<EOF
<pool type='dir'>
  <name>xdebbie</name>
  <target>
    <path>/var/lib/libvirt/xdebbie</path>
  </target>
</pool>
EOF
sudo virsh pool-define /tmp/pool.xml
sudo virsh pool-start xdebbie
sudo virsh pool-autostart xdebbie

# 5. Create config
sudo mkdir -p /etc/xdebbie
sudo cat > /etc/xdebbie/xdebbied.toml <<EOF
listen = "0.0.0.0:7443"
state_file = "/var/lib/xdebbie/state.json"
token_file = "/etc/xdebbie/token"

[[hosts]]
name = "$(hostname)"
uri = "qemu:///system"
bridge = "virbr-xdebbie"
storage_pool = "xdebbie"
cpu_overcommit = 2.0
mem_overcommit = 1.0
reserved_cpus = 2
reserved_memory_mib = 4096
EOF

# 6. Generate token
sudo mkdir -p /var/lib/xdebbie
TOKEN=$(openssl rand -hex 32)
echo "$TOKEN" | sudo tee /etc/xdebbie/token
sudo chmod 600 /etc/xdebbie/token

# 7. Create env file
cat > /etc/xdebbie/xdebbie_env <<EOF
export XDEBBIE_URL=https://$(hostname -f):7443
export XDEBBIE_CA=/etc/xdebbie/api-ca.pem
export XDEBBIE_TOKEN='$TOKEN'
EOF

# 8. Start server
sudo xdebbied serve
```

**After (Bootstrap)**:

```bash
# One command does it all
sudo xdebbied bootstrap
sudo xdebbied serve
```
